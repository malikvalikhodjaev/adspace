# Maydonlar server operations

Current product and workflow decision: [ADR-002](architecture/ADR-002-Maydonlar-server-MVP.md). The older ADR-001 describes the archived Sites prototype, not this server deployment.

Target: `malik@130.49.168.29`, alongside Marosim in `/home/malik/apps/adspace`. Public address: `https://maydonlar.fom-analytics.uz`; previous hostnames `https://maydon.fom-analytics.uz` and `https://adspace.fom-analytics.uz` remain as aliases and for existing player links. Redirects of ordinary pages are opt-in with `MAYDON_REDIRECT=1` after DNS propagation; the current service unit keeps them disabled. Private app port: `127.0.0.1:3002`. Existing dashboard and Marosim routes are preserved.

The app uses its own sessions and roles, email/password as a fallback, and a device-bound demonstration phone flow. The shown code is never sent by SMS and does not verify number ownership; a different browser cannot access the existing phone profile with that number alone. A SQLite WAL database stores shared state and assets metadata, and files stay in the private data directory. There is no dependency on Sites identity, D1, R2 or its hosting. The historical `.openai/hosting.json` is retained only as provenance; do not publish this server version using Sites. Old hosted account sandboxes have not been imported or deleted.

The administrator opens `/admin` directly; there is no public navigation link. An unauthenticated visit offers the existing email sign-in. The admin view and administrative API actions still require the server-side admin role; the path itself is not a credential.

The six seed surfaces are explicitly marked as demonstrations. Newly registered operators can create and publish their own surfaces, or save drafts; screen listings do not require platform approval. Each placement requires acceptance by every relevant screen owner; there is no separate platform content approval. New material requires fresh agreement acceptance and resets owner decisions. Browser player links are per-screen credentials with rotation/revocation; do not share them publicly.

New screens use explicit 10/15/30-second tariffs per single play. The customer chooses plays per day per screen; the quote is the sum of the matching screen tariffs times the chosen count and days. One reservation still occupies one concurrent calendar lane. The server checks the selected time window and conservatively limits play count by its physical duration divided by configured concurrent lanes. The player spaces due plays through the selected window, records starts and removes a creative after its daily quota. This is a browser-player signal, not independent physical-screen proof. Legacy screens retain their existing daily tariff until their owner explicitly switches pricing mode; agreed reservations are immutable during an active campaign. A serialized database transaction prevents overbooking. Unsubmitted drafts hold capacity for 30 minutes. Local time is Asia/Tashkent. The manifest is renewed every 10 seconds, its lease expires at the next minute boundary, and offline media is cached only for that lease. After expiry the player stops until it has a fresh schedule, avoiding indefinite playback of withdrawn material.

City and district selectors come from the Statistics Committee's official [SOATO workbook](https://stat.uz/images/soato-20_04_2022.xlsx), snapshot dated 2022-04-20. It contains 120 cities and 175 districts, including Tashkent city's 12 districts. It is a static source snapshot, not a live tax-authority API; update and revalidate it as administrative divisions change. Other-city coordinates must be supplied by the operator rather than inferred from a city name.

The customer calendar is `/?view=calendar&screen=<id>`; the owner calendar is `/?view=owner-calendar&screen=<id>` and requires ownership. Both show shared availability by date and hour. The customer can choose one displayed hour or the full operating window, then extend that daily interval across dates; the existing server-side capacity check remains authoritative. The owner sees requests and can close/reopen whole dates. There is no Google Calendar/Calendly account sync, hourly external-booking ledger, or ERP analytics yet.

`/devshow` is a public visual demonstration with synthetic content only. `/devshow/<screenId>` is the owner/admin-only live grid preview; its media API authorization is unchanged. Old `/display/<screenId>` bookmarks still render the same preview. Neither preview sends playback events or changes the campaign ledger. The physical-screen-facing player remains on `/player/<screenId>` and is separate from Devshow.

Media is inspected and rendered with FFmpeg/FFprobe in `runtime/media` using two processing threads and a bounded timeout. Original videos may be MP4 or WebM, pictures PNG or JPEG. Final video is H.264 MP4 at the target resolution and frame rate, without audio; images are rendered PNG. Camera capture uses the browser camera after an explicit user click. Manual crop, position, scale and time trimming plus cover/contain/stretch fit are available. Files and exact hashes survive restarts and are referenced by immutable test agreement snapshots.

One ID access and legal text are not available. The user approved in-account acceptance for the current service and later specified owner-only placement approval. No real payment processing, SMS delivery or verified phone OTP, Google OAuth, legal signature, fiscal receipts or physical CMS integration is claimed. Camera behavior must still be tested on actual phones. Human research materials and business-model hypotheses are in adjacent documents; real interviews are not yet conducted.

## Deployment and rollback

Releases live in `/home/malik/apps/adspace/releases`; `current` points to the active one. `deploy/publish.sh` validates exact release scope, checks local startup, initializes the private admin credential if absent, backs up the Cloudflare ingress config and adds the Maydonlar hostname while retaining the Maydon and AdSpace routes for existing links. Failed health checks restore the previous service unit, routing and release if available. Existing sites are checked after publication.

Persistent data and private administrator access are in `/home/malik/apps/adspace/data`. They are excluded from release archives and Git. Back up the whole data directory using SQLite's backup API for the database and a consistent copy of media; do not copy only the live database file while WAL writes are active. Retain prior release folders. For rollback, point `current` to the last verified release and restart `adspace.service`; schema changes require a separately tested data migration/restore plan.

Verification: `npm run typecheck`, `npm run build`, `npm run test:domain`, `node scripts/test-server.mjs`. The tests create separate private QA databases and subprocesses; they never change live data. `scripts/bootstrap-admin.mjs` creates the first administrator only if none exists and stores a randomly generated password in a private file, never in logs.
